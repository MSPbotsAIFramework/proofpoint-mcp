## Product design

### Goals / Non-goals

**Goals**

- G1: An agent using this connector can list and search quarantined messages, and release or
  delete one, when the tenant has configured Proofpoint Protection Server (PPS) credentials — in
  addition to the email-threat-review tools that already work today.
- G2: Tenants who only configure TAP credentials (today's only supported setup) keep working
  exactly as before: no new required header, no behavior change to any existing tool.

**Non-goals** (researched vendor limitations, not a product trade-off call)

- NG1: Creating, listing, or editing Proofpoint mail filtering policies or routes ("configure
  policies"). Confirmed 2026-10-30 across every Proofpoint API found (TAP, Essentials Interface
  API v1, Essentials Threat API, and Proofpoint Protection Server's REST API) that none exposes
  policy/route management — see the table above. The existing `proofpoint_policy_*` tools stay
  exactly as they are today (unchanged, still correctly labelled unavailable).
- NG2: DLP incidents / encrypted-message logs and Threat-Response message pull. Not part of the
  ticket's three named capabilities (threats / quarantine / policy); left unchanged.

### Acceptance criteria

- **AC1** — Given PPS credentials are present on the request, when `proofpoint_quarantine_list`
  is called with a folder filter, then it returns quarantined messages from that folder instead of
  the "Not available" error.
- **AC2** — Given PPS credentials, when `proofpoint_quarantine_search` is called with a query that
  matches a quarantined message's sender, recipient, or subject, then that message is returned.
- **AC3** — Given PPS credentials and a valid quarantined message id, when
  `proofpoint_quarantine_release` is called, then the message is released and the tool returns a
  confirmation (not an error); a following `_list`/`_search` for the same message no longer shows
  it in that quarantine folder.
- **AC4** — Given PPS credentials and a valid quarantined message id, when
  `proofpoint_quarantine_delete` is called, then the message is permanently removed and the tool
  returns a confirmation.
- **AC5** — Given a request carries only TAP credentials (no PPS headers), when any of the 4
  quarantine tools is called, then it returns a `not_configured` error naming the missing PPS
  headers — never the old "Not available: belongs to another Proofpoint product" message (that
  would now be inaccurate), and never a hard 401 at the gateway (TAP-only tenants must not be
  blocked from the rest of the connector).
- **AC6** — Given PPS headers are present but wrong, when a quarantine tool is called, then it
  returns an `unauthorized` error, not a 500 and not a silently empty result.
- **AC7** — Given PPS credentials, when `_release` or `_delete` is called with a message id that
  does not exist in quarantine, then it returns a `not_found` error.
- **AC8** — Given two different callers send different PPS credentials on two separate requests,
  when each calls `proofpoint_quarantine_list`, then each only sees their own tenant's PPS
  quarantine — no shared state or cache across requests (the same per-request-only guarantee the
  existing TAP and Reports clients already give).
- **AC9** (regression guard) — Given this ticket only adds quarantine support, when any
  `proofpoint_policy_*` tool is called, then it still returns today's exact "Not available" error
  — unchanged.
- **AC10** (regression guard) — Given existing tenant connections already call the 4 quarantine
  tool names with today's parameter sets, when `tools/list` is read after this change, then the
  tool names and required parameters for all 4 quarantine tools are identical to before — only the
  behavior behind them changes (per the contract declared in `tests/test_tools.py:25-27`).
- **AC11** — Given `proofpoint_status` already reports whether Reports API credentials were sent
  (`reports_credentials_sent`, `tests/test_api_client.py:442-445`), when `proofpoint_status` is
  called after this change, then it also reports whether PPS credentials were sent
  (`pps_credentials_sent`), following the same pattern.

### Open questions

- **Q1 (not blocking; assumption stated).** Proofpoint does not publish a single official PPS REST
  API reference the way it does for TAP. The most complete public mapping of the real API is the
  Cortex XSOAR "Proofpoint Protection Server v2" integration (built by Palo Alto against
  Proofpoint's actual API — see the Current-state table). Assumption: the dev leg implements
  against that documented command set and confirms exact endpoint paths/payload shapes against the
  target PPS instance's own admin-console API reference before merging (PPS exposes an interactive
  API doc once the "API" role is enabled, per that same prerequisite documentation). If the wire
  shapes differ in detail, that is an internal client adjustment, not a change to the tool
  contract (AC10), so it does not require redesign.
- **Q2 (not blocking; assumption stated).** `proofpoint_quarantine_search` takes one `query`
  string, but PPS's documented search needs at least one of sender / recipient / subject.
  Assumption: match `query` as an OR across sender, recipient, and subject (whichever PPS accepts
  as partial-match), preserving the tool's existing single-field search promise. See Decisions D4.

## Tech design

### Conclusion

Add a second, independent credential set (Proofpoint Protection Server) to this connector and
back the 4 existing quarantine tool stubs with it, without changing their names or parameters.
Leave policy (and DLP, message-pull) exactly as they are — researched and confirmed unavailable
through any Proofpoint API, not merely unimplemented.

### Where the current implementation lives

- Stub quarantine/policy/DLP/pull tools: `src/proofpoint_mcp/tools/unsupported.py:51-162`.
- Shared tool plumbing (error envelopes, `run_tool`, annotation constants, SIEM arg types):
  `src/proofpoint_mcp/tools/_common.py`.
- TAP/Reports HTTP client and credential dataclass: `src/proofpoint_mcp/api_client.py`.
- Per-request credential middleware and header names: `src/proofpoint_mcp/server.py:32-38,108-161`.
- Tool discovery / domain grouping and `proofpoint_status`: `src/proofpoint_mcp/tools/navigation.py`.
- Contract tests: `tests/test_tools.py`; client/middleware tests: `tests/test_api_client.py`,
  `tests/test_middleware.py`.

### Option analysis

- **Option A (chosen): add PPS as a second, optional credential set, real quarantine tools.**
  Matches what the ticket actually asks for and what Proofpoint actually offers. Reuses every
  existing pattern in this repo (optional-credential-set like Reports, `run_tool`/`ProofpointError`
  error handling, per-request-only credentials).
- **Option B: decline quarantine too, leave everything as "Not available" (do only a documentation
  pass).** Rejected — quarantine genuinely has a documented vendor API; declining it when it is
  buildable under-delivers relative to Option A for the same amount of researched certainty.
- **Option C: implement policy as a read-only "show the policy routes that applied to one message"
  tool, reusing data TAP's `smart_search_get_message` already returns (`policyRoutes`,
  `modulesRun`).** Rejected for this ticket — the ask was "configure" (a write), the read-only
  facts are already reachable today via `proofpoint_smart_search_get_message`, and no Proofpoint
  API writes policy. Left as a follow-up suggestion in Risks & dependencies, not built here.

### Decisions made by DEV01

No one could be asked (unattended design leg); these are the judgment calls made, with the
alternative that was not chosen:

- **D1 — Build quarantine via PPS rather than declining it for symmetry with policy.** Rejected
  alternative: decline the whole "manage quarantine" ask, matching how policy is being declined.
  Rejected because quarantine genuinely has a documented vendor API (Option A vs. B above) while
  policy does not — treating them the same would under-deliver what is actually buildable.
- **D2 — Keep "configure policies" undeliverable and unchanged.** Rejected alternative: Option C
  (a read-only policy-routes tool). Not chosen because the ticket asked for "configure" (a write),
  the read-only facts are already reachable through an existing tool, and no Proofpoint API writes
  policy — building a differently-scoped tool would be answering a question the ticket did not ask.
- **D3 — Model PPS credentials as 3 new optional headers, not a required, globally-breaking
  change.** Rejected alternative: make PPS credentials required alongside TAP's. Not chosen because
  it would break every existing TAP-only tenant connection (violates G2) for a capability
  (quarantine) that not every tenant will use.
- **D4 — `proofpoint_quarantine_search`'s single `query` matches OR across sender/recipient/subject
  (Q2).** Rejected alternative: require the caller to pick one of three separate parameters
  instead of one `query`. Not chosen because it would be a parameter-shape change to a tool whose
  contract (AC10) this ticket is committed to preserving.

To change any of these, say so in a comment and move this ticket back to `5b - ready for groom`.

### Data & API contract

New optional request headers (gateway-level, same place as the existing ones in
`server.py:32-38`):

| Header | Required | Description |
|---|---|---|
| `X-Proofpoint-Pps-Base-Url` | Only for quarantine tools | PPS REST API base URL, e.g. `https://<tenant>.pphosted.com:10000` (cloud) or the on-prem host. Must be `https://` and a bare host (no path/query/userinfo) — validated the same structural way as the existing TAP cluster-URL check, but without a `.proofpoint.com` suffix restriction (PPS hosts are tenant-specific and often on-prem; see Non-functional). |
| `X-Proofpoint-Pps-Username` | Only for quarantine tools | PPS API-role account username. |
| `X-Proofpoint-Pps-Password` | Only for quarantine tools | PPS API-role account password. Sent as HTTP Basic auth, same mechanism as the existing TAP principal/secret. |

| Tool | Params (unchanged) | New behavior |
|---|---|---|
| `proofpoint_quarantine_list` | `sender, recipient, subject, startDate, endDate, folder, page, per_page` (all optional) | Real PPS `quarantine-messages-list`-equivalent call when PPS credentials present; `not_configured` otherwise |

Error envelope shape is unchanged (`{"error": {"code", "message", "retryable"}}`,
`_json.error_envelope`); no new error `code` values are introduced — `not_configured`,
`unauthorized`, `not_found`, `invalid_argument`, `rate_limited`, `upstream_error` already cover
every case here via the existing `classify_status` table.

### Key flow / sequence

1. Agent calls `proofpoint_quarantine_release(message_id="...")` with both TAP and PPS headers set.
2. `GatewayCredentialsMiddleware` parses all headers into one `ProofpointCredentials` (unchanged
   TAP parsing; PPS fields added; a malformed PPS URL sets `header_error` instead of blocking).
3. `quarantine.proofpoint_quarantine_release` → `run_tool` → `client.has_pps_credentials` is
   `True` → `client.pps("POST", "<release path>", body={"message_id": ...})`.
4. `ProofpointClient.pps()` builds `Authorization: Basic <pps_username:pps_password>` and calls
   `_send`, which retries 5xx/network errors with backoff exactly as `.tap()` already does.
5. PPS responds; `classify_status` maps any 4xx/5xx to the standard envelope; a 2xx is returned to
   the agent as confirmation.

### Non-functional

- **Multi-tenant isolation (AC8):** PPS credentials follow the exact same per-request,
  never-stored, never-shared pattern already proven for TAP and Reports — one `ProofpointClient`
  instance per request, built from the request's own headers via the context var in `server.py`,
  nothing cached across requests. `ProofpointCredentials.__repr__` must redact
  `pps_username`/`pps_password` the same way it already redacts `principal`/`secret`.
- **Security:** PPS credentials are an admin-role account (not a scoped API key like TAP's service
  principal), so the no-log/no-store guarantee matters even more here. Existing log lines
  (`api_client.py:222-225`) only log `method`/`path`/`status`/`ms`/`attempt`, never headers or
  bodies — the new `pps()` path must keep using that same logging call, not add anything more
  detailed.
- **Host validation trade-off (flagged for reviewer attention):** the TAP cluster URL is restricted
  to the `.proofpoint.com` domain suffix (SSRF protection, since TAP's real host is always on that
  domain). PPS has no such fixed domain — cloud tenants are on `*.pphosted.com`, on-prem tenants
  are on an arbitrary customer host. `normalize_pps_base_url` therefore only enforces `https://`
  and a bare host, not a domain suffix. The credential itself (PPS admin password) is supplied by
  the same tenant that supplies the base URL, so the trust boundary is unchanged — a tenant can
  only point its own connector at a host of its own choosing — but this is a narrower check than
  the TAP one in the same file, so it is called out explicitly rather than silently copied.
- **Rate limits:** TAP and Reports have documented, enforced quotas (`_common.py:44-50`,
  `reports.py:27`); Proofpoint has not published an equivalent quota for the PPS REST API in any
  source found during this design. No special handling beyond the existing default (5xx/network
  errors retried with backoff, 4xx not retried) — if PPS throttling is observed in practice, that
  is a follow-up tuning change, not a contract change.
- **Idempotency:** releasing or deleting an already-released/-deleted message is expected to 404
  on the second call (mapped to `not_found`, AC7) — no new idempotency key is introduced; this
  matches how the rest of this connector already treats "acted on something that no longer exists."

### Rollout & rollback

Single repo, no cross-repo dependency, `release order: any` does not apply (nothing to sequence
against). No database, no migration. The tool contract (names/params) does not change, so there is
no client-side coordination needed — tenants that add PPS headers start getting real quarantine
data on their next call; tenants that do not are unaffected (G2). Rollback is a plain revert of
the merge commit; nothing persisted needs to be cleaned up.
