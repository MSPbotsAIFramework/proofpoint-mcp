## Product design

### Goals / Non-goals

**Goals**
- An MSP connecting their Proofpoint Essentials org to MSPbots Connector can let an AI client
  read Essentials domain and user inventory, and Essentials-specific threat/click/message
  events, the same way they already can for Proofpoint TAP.
- Credentials for Essentials are supplied per request (header-based), encrypted in transit,
  never stored by this server, and every call is logged by the surrounding gateway — this is
  the existing `proofpoint-mcp` contract already met for TAP; Essentials tools get the identical
  guarantee for free by going through the same client and middleware.
- A customer who only uses TAP today is completely unaffected: no new required header, no tool
  rename, no behavior change to an existing tool.

**Non-goals (this version)**
- No write operations against Essentials (no domain/user create, update or delete) — matches
  the repo's existing "read only" principle (`README.md:13`); see Open questions.
- No Essentials Organization / Features / Licensing / Reporting / Package tools yet — the exact
  field names could not be confirmed from a static page fetch during design (see "Scope split",
  Risk R3). Domains, Users and the Threat API cover the ticket's actual ask (live, read, logged
  access) and are fully confirmed from vendor docs.
- No UI changes — this is an MCP server with no interface.

### Acceptance criteria

- **AC1**: Given valid Essentials Admin credentials (`X-Proofpoint-Essentials-User` /
  `X-Proofpoint-Essentials-Password`) are sent, When the client calls `tools/list`, Then the
  Essentials domain and user tools appear in the list alongside the existing TAP/Reports tools
  (tool count goes up; no existing tool is removed or renamed).
- **AC2**: Given valid Essentials Admin credentials for an org, When the client calls
  `proofpoint_essentials_list_domains`, Then it returns that org's domains as JSON, paginated
  and capped the same way other list tools in this server are (`offset`/`next_offset`).
- **AC3**: Given valid Essentials Admin credentials, When the client calls
  `proofpoint_essentials_get_user` with an email that does not exist in that org, Then it
  returns a `not_found` error envelope (not an exception, not an empty 200).
- **AC4**: Given valid Essentials Threat API credentials (Integration Key/Secret), When the
  client calls `proofpoint_essentials_threat_get_messages_blocked` with no time arguments, Then
  it returns the last hour of blocked-message threat events, shaped and capped the same way
  `proofpoint_tap_get_messages_blocked` already is.
- **AC5 (no credentials)**: Given no Proofpoint credentials of any kind are sent, When the
  client sends any `/mcp` request, Then it gets HTTP 401 naming all three credential options
  (TAP, Essentials Admin, Essentials Threat) — this replaces today's "TAP is always required"
  401, see Tech design §7 Non-functional / security.
- **AC6 (backward compatibility)**: Given only TAP credentials are sent (no Essentials
  headers), When the client calls an existing TAP tool, Then it behaves exactly as before
  (200, same shape); When it calls an Essentials tool, Then it gets a `not_configured` error
  naming the missing Essentials headers — it does not get a 401 at the gateway and it does not
  silently try TAP credentials against the Essentials API.
- **AC7 (error shape)**: Given an Essentials Admin or Threat API call fails upstream (401, 404,
  429 or 5xx), When the tool runs, Then the error comes back as the same
  `{"error":{"code","message","retryable"}}` envelope already used by every other tool in this
  server, with the same `code` taxonomy (`unauthorized`, `not_found`, `rate_limited`,
  `upstream_error`, ...).
- **AC8 (multi-tenant isolation)**: Given two concurrent requests carry two different
  organizations' Essentials credentials, When each calls a tool, Then each sees only its own
  org's data, and neither request's credentials or response are cached, reused or visible to
  the other — this is the existing per-request isolation design extended to the new credential
  fields, not a new mechanism.

### Open questions

- **[assumed, does not block]** Essentials Admin tools in v1 are read-only
  (list/get only, no create/update/delete) even though the vendor API supports POST/PUT/DELETE
  on domains and users. This mirrors the repo's existing TAP-is-read-only principle and the
  ticket's own wording ("give... AI live access", not "let AI manage domains"). If product wants
  write tools later, that is a new ticket with its own safety review (destructive-tool
  annotations, audit requirements) — Tech design §4 and §9 would need revisiting.
- **[assumed, does not block]** Regional stack selection for the Admin API and SIEM
  host for the Threat API are both caller-supplied via optional headers (defaulting to `us1`
  and `us-siem` respectively), the same pattern `X-Proofpoint-Cluster-Url` already uses for TAP
  (`server.py:91-105`). If assumed wrong, Tech design §5 header table needs a different default.
- **[does not block]** Exact field names for Organization/Features/Licensing/
  Reporting/Package resources are not yet confirmed (the live interactive spec page is
  client-rendered and could not be scraped headlessly — see Current state). These resources are
  out of v1 scope (see Scope split) specifically because of this gap, so it does not block this
  design; dev leg confirms the live docs only if/when that follow-up ticket is picked up.

## Tech design

### Conclusion

Add Proofpoint Essentials as new tool modules inside the existing `proofpoint-mcp` repo, not a
new repo. Reuse the repo's existing client (`ProofpointClient`), request pipeline (`_send`),
error envelope, and — for the Threat API specifically — the exact SIEM windowing/shaping/tool-
registration code already written for TAP, since Essentials Threat uses the identical
`/v2/siem/<area>/<status>` path shape. The only structural change to existing code is the
credential-gating rule in the middleware: today TAP credentials are unconditionally required;
this changes to "at least one of TAP / Essentials Admin / Essentials Threat must be present",
which is backward compatible for every existing TAP caller.

### Where the current implementation lives

- `src/proofpoint_mcp/server.py:32-38` — header name constants, `REQUIRED_HEADERS` /
  `OPTIONAL_HEADERS`.
- `src/proofpoint_mcp/server.py:108-161` — `GatewayCredentialsMiddleware`: reads headers, 401s
  on missing required ones, builds `ProofpointCredentials`, sets the per-request contextvar.
- `src/proofpoint_mcp/server.py:91-105` — `normalize_base_url`: validates a caller-supplied base
  URL is https on an allowed host suffix. Written TAP-specific (`ALLOWED_HOST_SUFFIX` from
  `config.py:26`); needs generalizing to take the suffix as a parameter so Essentials headers can
  reuse it instead of duplicating the validation.
- `src/proofpoint_mcp/api_client.py:101-113` — `ProofpointCredentials` dataclass (frozen,
  redacted `__repr__`).
- `src/proofpoint_mcp/api_client.py:116-244` — `ProofpointClient`: `tap()` (Basic auth) and
  `reports()` (Bearer, lazily fetched token) are the two existing per-API methods; both funnel
  through the shared `_send()` (retry/backoff/error classification, `api_client.py:196-244`).
  This is the method pair to copy for `essentials_admin()` and `essentials_threat()`.
  `classify_status` / `_STATUS_TO_CODE` (`api_client.py:65-87`) is the shared HTTP→error-code
  mapping, reused as is.
- `src/proofpoint_mcp/tools/_common.py:131-217` — `siem_window`, `fetch_siem`, `shape_siem`,
  `siem_lists`: the generic SIEM time-window validation and response-shaping logic. Currently
  called only via `client.tap(...)` inside `fetch_siem` (`_common.py:179-192`).
- `src/proofpoint_mcp/tools/tap.py:72-129` — `_register_siem_tool` + `SIEM_TOOLS`: registers one

- `src/proofpoint_mcp/tools/people.py:36-49` — `people_page` / `locate` / `resume_fields`
  (`_common.py:85-105`): the paging-by-offset pattern already built for a paginated TAP list API

- `src/proofpoint_mcp/tools/navigation.py:29-137` — `DOMAINS` registry + `proofpoint_navigate` +
  `proofpoint_status`: the place that already aggregates "is this credential set configured and
  authorized" per API (`has_reports_credentials`, TAP probe call). Essentials needs the same two
  additions.
- `src/proofpoint_mcp/server.py:164-182` — `create_mcp_server`: the module registration loop.

### Option analysis

| Option | Approach | Pros | Cost | Verdict |
|---|---|---|---|---|
| A. New sibling repo `proofpoint-essentials-mcp` | Separate codebase, separate deploy, separate credential set | Clean credential separation by construction | Forks the "Proofpoint" surface across two repos an operator has to know to look in both of; `scripts/new_repo.py` actively refuses to create it (exit 2, vendor-token collision guard) unless a human overrides that judgment | Rejected |
| B. Extend `proofpoint-mcp` with new tool modules (chosen) | New `tools/essentials_admin.py`, `tools/essentials_threat.py`; extend `api_client.py`, `server.py` credential gating | One Proofpoint connector to configure, reuses the client/retry/error/SIEM-windowing code almost entirely; matches `references/mcp-track.md` 2.1's "capability gap in an existing repo → extend it" rule | Middleware's "credentials required" rule has to become "at least one set required" — the one place existing behavior changes, and it needs its own tests (AC5/AC6) | **Chosen** |
| C. Bolt Essentials calls onto the existing `tap()`/`reports()` client methods instead of adding `essentials_admin()`/`essentials_threat()` | Fewer methods on `ProofpointClient` | Less code | Essentials Admin uses a completely different auth shape (literal `X-User`/`X-Password` headers, not Basic) and a different base host family; forcing it through `tap()`'s Basic-auth path would mean branching inside one method instead of two small, readable ones — `api_client.py`'s own pattern (one method per credential shape: `tap()` vs `reports()`) argues against this | Rejected |

**Example — list domains:**

Request: `tools/call proofpoint_essentials_list_domains {"org_domain": "example.com"}`
with `X-Proofpoint-Essentials-User` / `-Password` headers set.

Success (200 from Proofpoint, shaped the same way other list tools are):
```json
{"domains": [{"domain": "example.com", "verified": true}, ...], "count": 12}
```

Missing Essentials headers:
```json
{"error": {"code": "not_configured", "message": "Proofpoint Essentials Admin credentials are missing for this request (X-Proofpoint-Essentials-User, X-Proofpoint-Essentials-Password).", "retryable": false}}
```

Vendor rejects the credentials (401 from Proofpoint):
```json
{"error": {"code": "unauthorized", "message": "Proofpoint returned HTTP 401 for orgs/example.com/domains: the credentials were rejected (check username / password and admin URL)", "retryable": false}}
```

**Backward compatibility**: no existing header, tool name or response shape changes. The single
behavioral change is the 401 condition at the gateway (today: TAP headers always required; after:
at least one of the three sets required) — a caller already sending TAP headers sees no change at
all.

### Key flow / sequence

```
AI client --/mcp, X-Proofpoint-Essentials-User/-Password--> GatewayCredentialsMiddleware
  --at least one credential set present?--
    no  -> 401 {required: none satisfied, lists TAP / Essentials Admin / Essentials Threat}
    yes -> build ProofpointCredentials (TAP fields empty if not sent) -> contextvar -> FastMCP
tools/call proofpoint_essentials_list_domains
  -> run_tool -> client_factory() -> has essentials_admin creds?
       no  -> not_configured envelope (TAP tools, if called, are unaffected)
       yes -> client.essentials_admin("GET", "/orgs/{org}/domains") -> _send() (retry/backoff,
              same as every other call) -> classify_status on failure -> JSON result or envelope
```

### Non-functional

- **Idempotency & concurrency**: unaffected — the new methods reuse the existing stateless,
  per-request `ProofpointClient` instance and the shared cookie-free `httpx.AsyncClient`
  (`api_client.py:37-62`); no new shared state is introduced.
- **Performance**: Essentials Threat has the same 1800-call/24h rolling quota as TAP, handled by
  the existing `_STATUS_TO_CODE`/429 logic unchanged. Essentials Admin's rate limit is not
  published anywhere I found (not in the docs fetched for this design); until confirmed,
  Essentials Admin calls are treated like Reports calls today — retried on 5xx/network errors,
  not retried on 429 — same policy, same code path.
- **Security**: credentials arrive only as per-request headers, never logged (the dataclass
  `__repr__` pattern at `api_client.py:112-113` is extended to the new fields, same redaction),
  never written to disk; the admin/threat base-url headers are validated against the
  `.proofpointessentials.com` suffix the same way `X-Proofpoint-Cluster-Url` is validated against
  `.proofpoint.com` today (`server.py:100-101`), so a malformed header cannot redirect credentials
  to another host — it returns `invalid_argument` the same way a bad TAP cluster URL does.
- **Multi-tenant isolation**: unchanged mechanism — `contextvars` scope credentials to one HTTP
  request (`server.py:42-48`); AC8 is a test of this extended to the new fields, not a new
  isolation mechanism.
- **Observability**: every new call funnels through `_send()`, so it gets the existing
  `proofpoint_api method=... path=... status=... ms=... attempt=...` log line
  (`api_client.py:222-225`) for free, with no additional logging code to write.

### Decisions made by DEV01 (technical design adjustments, not covered by an AC)

- **Essentials Admin list pagination is client-side, not server-side.** The tech design's change
  list said to reuse `tools/people.py`'s pattern (send `page`/`size` to the vendor). I did not:
  that pattern only produces correct results if the vendor actually slices its response to the
  requested page, which the Essentials Admin API's pagination contract could not confirm (no
  account available — Risk R3 in the tech design covers the adjacent resources, the same gap
  applies here to the exact paging mechanics of Domains/Users). Blindly sending `page`/`size` and
  trusting the vendor to honor it risks a silent correctness bug (wrong slice) that would not
  show up against a mock built to match my own assumption. Instead `essentials_admin.py` fetches
  each org's full list once per call and pages it client-side with the same `locate`/
  `resume_fields` helper `tools/search.py`'s `proofpoint_smart_search_trace` already uses for a
  result fetched in one shot — correct regardless of what the vendor's own paging does, at the
  cost of re-fetching the full list on every page for very large organizations. Documented in
  `README.md` ("Paging by offset") and `tools/essentials_admin.py`'s module docstring.
- **`path_segment` moved from `tools/threats.py` to `tools/_common.py`.** `essentials_admin.py`
  needs the same "non-blank, URL-encoded path segment" helper `threats.py` already had (private,
  under the name `_segment`); moved it to the shared module instead of a second copy, and updated
  `threats.py`'s two call sites (plus a third inside `proofpoint_threat_list_families` that a
  first pass of this refactor missed — caught by `test_list_families` failing with a `NameError`
  on the now-unimported `quote`, fixed before this stub).
- **`normalize_base_url` generalized to allow a non-empty default path.** The original function
  enforced a bare host with no path (correct for TAP, whose base URL never has one). The
  Essentials Admin API's base legitimately includes `/api/v1`; a literal reuse would reject the
  default value itself the moment a caller tried to override the regional stack. Generalized to
  compare the caller's path against `urlsplit(default).path` instead of only `("", "/")` — TAP's
  behavior (default path `""`) is unchanged, verified by the full pre-existing
  `test_cluster_url_normalised`/`test_cluster_url_rejected` suite still passing unmodified.
- **Essentials Admin/Threat malformed-URL errors stay on the shared `header_error`**, matching
  the TAP cluster URL precedent from this ticket's own tech design, rather than PRD-21254's newer
  `pps_header_error` pattern (which narrows the blast radius to only the credential set's own
  tools). Both conventions now coexist in this codebase for different optional credential sets —
  noted here so a future ticket touching either pattern makes a conscious choice instead of
  assuming there is only one convention. Not an AC-driven requirement either way; flagging as a
  reviewer-visible judgment call per `legs/dev.md`'s "put choices and reasoning in the doc" rule.
